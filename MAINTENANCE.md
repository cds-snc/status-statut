# Maintaining this repo

Operator's guide for `cds-snc/status-statut`, our [Upptime](https://github.com/upptime/upptime)
instance. `README.md` is generated by Upptime — keep documentation here instead.

> Upstream docs: <https://upptime.js.org/docs> · Action source: <https://github.com/upptime/uptime-monitor>

---

## 1. How it works

There is no server and no database. The repo *is* the database:

| Artifact | Where | Written by |
| --- | --- | --- |
| Latest status of each site | `history/<slug>.yml` (overwritten in place) | Uptime CI / Response Time CI |
| **Historical** response times | the **git commit history** of `history/<slug>.yml` | same |
| Uptime %, incidents | GitHub **Issues** labelled `status,<slug>` | Uptime CI |
| Badges (shields.io endpoints) | `api/<slug>/*.json` | Summary CI |
| Response-time charts | `graphs/<slug>.png` | Graphs CI |
| Public status page | `gh-pages` branch → <https://status-statut.cds-snc.ca> | Static Site CI |

Three facts that explain most surprises:

1. **Graphs are built from commits, not file contents.** `@upptime/graphs` calls
   `listCommits({ path: "history/<slug>.yml" })` and parses the response time out of each commit
   message. No commits in a period ⇒ a hole in the graph, even if monitoring ran fine.
2. **The 5-minute check usually commits nothing.** `command: update` only commits when status
   *changes*; otherwise it logs `Skipping commit, status is up`. The routine datapoint comes from
   the **daily** `command: response-time` run, which force-commits every site. Normal graph
   resolution is therefore **one point per site per day** (~21 commits/day), not one per 5 minutes.
3. **Uptime % comes from Issues**, not from history commits. Probing and recording can fail
   independently — see §7.

## 2. Workflows

Independent cron jobs sharing one repo. Nothing calls anything else except where noted.

### Upptime-generated (modified by us — see §6)

| File | Name | Trigger | Command | Effect |
| --- | --- | --- | --- | --- |
| [uptime.yml](.github/workflows/uptime.yml) | Uptime CI | `*/5 * * * *` | `update` | Probes every site; opens/closes incident Issues **on status change only**. Runs on our CodeBuild runner. |
| [response-time.yml](.github/workflows/response-time.yml) | Response Time CI | `0 23 * * *` | `response-time` | Same probe, force-commits every site. **This is what feeds the graphs.** |
| [graphs.yml](.github/workflows/graphs.yml) | Graphs CI | `0 0 * * *` | `graphs` | `npx @upptime/graphs` → `graphs/*.png` |
| [summary.yml](.github/workflows/summary.yml) | Summary CI | `20 0 * * *` | `readme` | Rewrites `README.md` between markers + `api/*/*.json` badges |
| [site.yml](.github/workflows/site.yml) | Static Site CI | `0 1 * * *` | `site` | Builds `@upptime/status-page`, deploys to `gh-pages` |
| [setup.yml](.github/workflows/setup.yml) | Setup CI | push to `.upptimerc.yml` | `response-time`, `readme`, `site` | Applies a config change immediately instead of waiting for the crons. Upstream's `update-template` step is removed — **see §6**. |

Ordering is implied by the crons only: `response-time` 23:00 → `graphs` 00:00 → `summary` 00:20 →
`site` 01:00. They are staggered so no two ever run at once (each takes 20–80s). If Response Time CI
is late, Graphs CI renders yesterday's data and self-corrects the next night.

All six check out `${{ github.head_ref || github.ref_name }}` rather than the SHA at trigger time,
which narrows the window in which a merge to `main` can make their `git push` fail.

**Never put two workflows in one `concurrency` group here.** GitHub holds one pending run per group
and a new arrival *replaces* it, so a shared group silently skips whole workflows — losing a day of
history with no failure to alert on. Only `uptime.yml` (`-upptime-probe`) and `setup.yml`
(`-upptime-setup`) have groups, each alone, so an eviction can only ever replace a duplicate of the
same workflow. The four daily jobs rely on staggered crons instead.

Push races cannot be fully eliminated — upptime pushes unconditionally and never rebases — but they
surface as a one-off `failure` that clears on the next run, which is strictly better than a silent
skip.

Deleted on purpose — do not let `update-template` recreate them: `update-template.yml`, `updates.yml`.

## 3. Secrets and tokens

Repo secrets: `CANADALOGIN_HEADER`, `SUPERSET_HEADER`, `NOTIFICATION_SLACK`,
`NOTIFICATION_SLACK_STRATEGY`, `NOTIFICATION_SLACK_WEBHOOK_URL`, `NOTIFICATION_SLACK_WEBHOOK`
(stale duplicate), `STATUS_OPS_WEBHOOK`.

`$SUPERSET_HEADER` / `$CANADALOGIN_HEADER` are interpolated into `headers:` in
[.upptimerc.yml](.upptimerc.yml); the action reads them from plain env vars.

Pass secrets to the action **individually**, never as a whole-context blob
(`SECRETS_CONTEXT: ${{ toJson(secrets) }}`). That pattern matches known exfiltration attacks and
GitHub will freeze the workflow — it is what caused the §7 outage.

Never interpolate `${{ ... }}` directly into a `run:` block. Values such as a ref or branch name can
contain shell metacharacters, and the expression is substituted into the script before bash sees it
([worked example](https://www.kenmuse.com/blog/the-hidden-danger-in-git-ref-names/)). Bind them to
`env:` and quote the variable instead, and build JSON payloads with `jq -n --arg` rather than string
concatenation. Passing an expression to an action's `with:` input is safe — inputs reach the action
as environment variables, never through a shell.

**There is no `GH_PAT`, and none is needed.** Everything runs on `GITHUB_TOKEN` (repo default
workflow permission is `write`), which covers all writes to `history/`, `api/`, `graphs/`,
`README.md` and `gh-pages`. The only thing that needs more is `update-template`, which we don't
want (§6). Our org restricts PATs; that restriction costs us nothing here.

If a GitHub App is ever introduced anyway, use upstream's convention — `vars.GH_APP_ID` +
`secrets.GH_APP_PRIVATE_KEY`, token resolved as
`${{ steps.app_token.outputs.token || secrets.GH_PAT || github.token }}` — so a future
regeneration doesn't overwrite it.

## 4. Routine tasks

**Add / remove a monitored site.** Edit `sites:` in [.upptimerc.yml](.upptimerc.yml) (name, url,
optional `headers:`, `assignees:`) and merge to `main`. Setup CI then refreshes data, README, graphs
and the published page automatically — no manual dispatch needed. Removing a site does **not**
delete its history.

**Change the status page.** Everything under `status-website:` in `.upptimerc.yml` — theme, nav,
`customHeadHtml`/`customBodyHtml`/`customFootHtml`, `i18n:` strings. Then `gh workflow run site.yml`.

**Edit the README.** Summary CI rewrites only line 1's title, the workflow badge lines (by regex,
anywhere in the file), and everything between `<!--start: status pages-->` and
`<!--end: status pages-->`. Prose outside those markers survives — but put real docs here instead.

**Force a full refresh.** Run these in order, waiting for each to finish (20–80s) — they all commit
to `main`, so overlapping them causes push failures:

```bash
gh workflow run response-time.yml && gh run watch "$(gh run list -w response-time.yml -L1 --json databaseId --jq '.[0].databaseId')"
gh workflow run graphs.yml     # then repeat the watch pattern for each
gh workflow run summary.yml
gh workflow run site.yml
```

**Upgrade `upptime/uptime-monitor`.** Renovate opens the PR. Review the diff for behaviour changes
in `src/update.ts`, then watch the first scheduled run after merge — a version bump edits the
workflow file and can re-trigger GitHub's workflow scanner.

**Record a monitoring outage.** Open an issue labelled `maintenance` covering the window and close
it. Upptime renders these as *Past Scheduled Maintenance*; unlike `status`-labelled issues they are
not counted as downtime.

## 5. Health checks

Run monthly, or first thing when someone reports a stale graph.

```bash
# 1. Is data landing? Expect ~21 commits/day, every day. This is the canary.
git log origin/main --format='%ad' --date=format:'%Y-%m-%d' --since='30 days ago' -- history/ \
  | uniq -c

# 2. Are scheduled runs executing? `action_required` = GitHub froze the workflow (§7).
gh run list --workflow=uptime.yml --limit 50 --json conclusion,createdAt \
  --jq 'group_by(.conclusion)[] | {(.[0].conclusion): length}'

# 3. Any workflow silently disabled?
gh api repos/cds-snc/status-statut/actions/workflows --jq '.workflows[]|"\(.state)\t\(.name)"'
```

### Automated alerting

Two layers, because per-run alerts cannot see every failure mode.

**Per run** — [workflow-failure.yml](.github/workflows/workflow-failure.yml) posts to Slack via
`STATUS_OPS_WEBHOOK`, with the conclusion in the message so a frozen run reads differently from a
broken one:

| Workflow | Alerts on |
| --- | --- |
| Uptime CI (every 5 min) | `action_required`, `startup_failure` |
| Everything else (daily) | those, plus `failure` and `timed_out` |

Uptime CI is deliberately exempt from `failure`. A single failed probe is not actionable — the most
common cause is a `git push` losing a race with a merge to `main`, which the next run fixes on its
own. `action_required` is never transient, so it still pages immediately.

**Daily** — [monitoring-health.yml](.github/workflows/monitoring-health.yml) runs at 12:30 UTC and
alerts if any of these hold:

- no commit to `history/` in over 25h,
- any Uptime CI run frozen as `action_required` in the last 24h,
- Uptime CI success rate under 40%, or no runs at all.

This is the layer that matters. It checks the *outcome* rather than the runs, so it catches
workflows that report `success` while recording nothing — the failure mode that cost eight weeks of
history in §7, and the one no run-level alert can see. Tune the thresholds via the `env:` block.

The canary is itself watched: it exits non-zero when unhealthy and is listed in
`workflow-failure.yml`, so a crash, a bad webhook or an invalid workflow file still alerts. The
trade-off is that a genuinely unhealthy day sends two messages — the canary's detailed one and a
terse per-run one for the same run. That is deliberate: a watchdog that can fail silently is worse
than one that occasionally repeats itself.

`action_required` is worth understanding: GitHub freezes a run pending human approval, scheduled
runs have nobody to approve them, and the run then expires as *completed*. It is not a failure, and
GitHub surfaces it nowhere else.

## 6. Why `update-template` is not in `setup.yml`

Upstream's Setup CI starts with `command: update-template`, which regenerates all 8 Upptime
workflow files from upstream templates and prunes the data directories. **We removed that step.**

It never succeeded here anyway — the push is rejected because `GITHUB_TOKEN` lacks `workflows`
permission. Older action versions swallowed that error and reported success; since v1.41.1 it fails
visibly, which is what made Setup CI go red on every `.upptimerc.yml` change.

The failing step was the only thing protecting this repo's customisations. Had it ever been given a
workflow-write token:

| Customisation | Fate | Recoverable? |
| --- | --- | --- |
| `runs-on: codebuild-…` | → `ubuntu-latest` | ✅ set `runner:` in `.upptimerc.yml` |
| Cron schedules | → upstream defaults | ✅ set `workflowSchedule:` |
| `SECRETS_CONTEXT` | → ~100-name allowlist | ✅ set `secrets:` |
| **SHA-pinned actions** | → floating tags (`actions/checkout@v6`, …) | ❌ no config hook |
| `update-template.yml`, `updates.yml` | recreated | ❌ |
| `.templaterc.json` | deleted | ❌ |
| `api/`, `graphs/`, `history/` for retired slugs | **pruned** (~20 services) | ❌ irreversible |

The un-pinning is the dealbreaker: it contradicts our OSSF Scorecard posture and would put
`update-template` and Renovate in a loop undoing each other.

**Do not re-add the step.** A comment in [setup.yml](.github/workflows/setup.yml) says the same
thing at the point where it used to be.

The rest of Setup CI was kept: those steps are safe under `GITHUB_TOKEN` (including the
`workflow-dispatch` of Graphs CI) and give it its real value — applying a `.upptimerc.yml` change
immediately instead of waiting for the nightly crons.

Upstream's "do not edit this file" banner has been replaced with an accurate one in all six files.
It claimed changes are overwritten when the template updates daily; that never happened here, the
workflow meant to do it was deleted in [#487](https://github.com/cds-snc/status-statut/pull/487),
and the files already carried years of our edits (SHA pins, CodeBuild runner label, user-agent
headers). There is no `.upptimerc.yml` key that disables regeneration, so editing them was the only
option.

## 7. Why historical data has a gap (Jul–Sep 2026)

Resolved 2026-09-23 by [#505](https://github.com/cds-snc/status-statut/pull/505). Kept here because
the gap is permanently visible in the year-scale graphs.

**Cause.** Since 2022, `uptime.yml` and `response-time.yml` passed the entire secrets object to the
action as `SECRETS_CONTEXT: ${{ toJson(secrets) }}`. On 2026-07-28 GitHub shipped
[malicious-workflow detection](https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/),
which matched that pattern and held both workflows for human approval:

> GitHub detected that this workflow file may be malicious. It will not run until someone with
> write access approves it.

Scheduled runs have nobody to approve them, so they expired as `action_required` — a *completed*
conclusion, not a pending one, so there was never an approval queue to work through. Graphs CI,
Summary CI and Static Site CI were unaffected (they pass only `GITHUB_TOKEN`), so the status page
kept publishing while the data behind it went stale.

**What was actually lost.** Probing and recording failed independently:

| Window | Probes run | Outcome |
| --- | --- | --- |
| Jul 29 – Aug 7 | 137 | 36 ok / 101 failed |
| **Aug 8 – Aug 27** | **0** | **blind spot — nothing measured** |
| Aug 28 – Sep 6 | 1140 | 1138 ok — monitored, not recorded |
| Sep 7 – Sep 22 | 2100 | 892 ok / 1204 frozen |

No incident issues were opened in the whole window, and uptime % derives from Issues — so the
**availability record is intact**. The gap is confined to response-time graphs.

**It cannot be backfilled.** The measurements existed only in Actions run logs, and log retention
here is ~3 days. Do not synthesise replacements: backdated commits render as real measurements on a
public Government of Canada status page.

**The graphs heal themselves** — each filters on recency, so day/week/month views clear within a
month of the fix. Only the 1-year graph carries the gap, until ~Sep 2027.

**Watch the inverse artifact:** uptime will report ~100% for the year including Aug 8–27, when
nothing was measured. Annotate that with a `maintenance` issue (§4) rather than leaving it implied.

## 8. Working locally

The action is a plain Node 24 program. There is no upstream local-dev story, so this is assembled
from its source. Every command ends in `git commit` + `git push`, so **always use a throwaway clone
with the remote redirected.**

```bash
# Build the action once
git clone https://github.com/upptime/uptime-monitor.git /tmp/uptime-monitor
cd /tmp/uptime-monitor && nvm use 24 && npm ci && npm run build

# Sandbox the status repo so nothing can reach GitHub
cd /tmp && git init --bare fake-origin.git
git clone https://github.com/cds-snc/status-statut.git /tmp/sandbox
cd /tmp/sandbox && git remote set-url origin /tmp/fake-origin.git

# Run a command (see the switch in uptime-monitor/src/index.ts)
INPUT_COMMAND=update \
GITHUB_REPOSITORY=cds-snc/status-statut \
GH_PAT="$(gh auth token)" \
SUPERSET_HEADER=... CANADALOGIN_HEADER=... \
node /tmp/uptime-monitor/dist/index.js
```

`INPUT_COMMAND` accepts `update`, `response-time`, `graphs`, `readme`/`summary`, `site`,
`update-template`.

- `update` / `response-time` hit the **real** endpoints and can open real Issues. Use `readme` or
  `site` for anything cosmetic.
- Without `SUPERSET_HEADER` / `CANADALOGIN_HEADER`, those sites report `down` locally. Expected.
- **Never** run `update-template` against a real clone (§6).
- `site` runs `npm i @upptime/status-page && npm run export`, output in
  `site/status-page/__sapper__/export/` — serve it with any static file server. Fastest loop for
  `status-website:` changes.

*Derived from the action's source; not executed end-to-end. Verify in the sandbox before relying
on it.*

## 9. Standing risks and limits

| Risk | Action |
| --- | --- |
| `update-template` re-added to `setup.yml` (by a person or a template regeneration) | Would un-pin actions and delete retired history — see the comment in the file and §6 |
| Pressure to add a PAT or App token "to fix Setup CI" | The fix is removing the step, not adding a token (§3) |
| Whole-secrets blob reintroduced by a careless merge | Review every diff to `uptime.yml` / `response-time.yml` |
| `security.txt` `Expires: 2027-04-01` | Renew before it lapses |
| Stale `NOTIFICATION_SLACK_WEBHOOK` secret; "Update Template CI" listed in `workflow-failure.yml` | Cosmetic cleanup |

Structural limits worth knowing before anyone proposes replacing this:

- **Coarse history** — one datapoint per site per day.
- **One region** — GitHub-hosted runners / our `ca-central-1` CodeBuild runner.
- **Best-effort scheduling** — GitHub drops `*/5` cron runs under load; healthy days land ~125 of an
  expected 288.
- **Silent failure modes** — as §7 showed, the page keeps rendering while data goes stale.

Multi-region probing or a real SLO with sub-daily resolution are the triggers to look at a hosted
checker. Workflow complexity is not — that is one step in one file.
